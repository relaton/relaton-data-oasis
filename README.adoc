= Publications bibliographic data for Relaton-OASIS

This repository is used by Relaton-OASIS to represent known publications.

Data is stored in Relaton YAML format.

This repository uses the OASIS flavor of the
https://github.com/relaton/relaton[relaton] gem to fetch the documents, and runs
daily. `relaton-oasis` no longer exists as a gem of its own -- the flavor lives
in the combined `relaton` gem. `crawler.rb` parses
https://www.oasis-open.org/standards/ and stores the documents in the `data`
directory.

== Indexes

Two indexes are published. `relaton/support`'s shared `crawler.yml` zips and
commits both; nothing in this repository zips.

`index-v2`:: The current, pubid-keyed index. Written by
`Relaton::Oasis::DataFetcher` itself, with each row's `:id` a
`Pubid::Oasis::Identifier` serialised to its `_type: pubid:oasis:standard` hash.
The `number` field holds the specification name -- `OSLC-CoreShapes`,
`amqp-core` -- which is the key `Relaton::Index::Type` sorts and
binary-searches on. It deliberately clusters: every version, stage and part of
one specification shares it. The 605 rows published today give 309 buckets, the
largest 25.

`index-v1`:: The legacy index, a flat list of `{ :id, :file }` rows whose `:id`
is the printed identifier string -- `OASIS OSLC-CoreShapes-3.0-PS01-Pt8`. It is
kept alive for every released `relaton` line that still reads `index-v1.zip`
from this branch. The gem no longer writes it, so `crawler.rb` rebuilds it here
through `index_builder.rb`.

`index-v1` is rebuilt from the `data/` tree rather than derived from the
`index-v2` rows. Each document's primary `docidentifier` content *is* the v1 row
id, because that is the string relaton writes on both sides of the migration, so
reading it keeps the rebuild independent of which index the gem happens to
write, and free of pubid entirely. Only that one field is read -- no bibitem
deserialization -- so data-model drift cannot break it. relaton-data-iana,
relaton-data-etsi and relaton-data-bipm carry the same arrangement.

A `data/` walk sees one identifier per file, though, so an identifier whose
document was overwritten by another would vanish without trace. The builder
therefore cross-checks against the index the fetch just wrote and fails the
crawl, naming the lost identifiers, rather than publish a short index over a
whole one.

Run the specs that guard all of this with:

[source,sh]
----
bundle exec rspec
----

== Dependency pins

`Gemfile.lock` is git-ignored, so a crawl resolves every pin fresh. Verify with
`bundle list | grep -E 'relaton|pubid'` before trusting a generated index.

`pubid` is pinned to `pubid/pubid@main`, which carries the OASIS flavor and
`Pubid::Oasis::Identifier#number`. The latest release, 2.0.0.pre.alpha.9,
predates that attribute, which is why the pin is a git pin.

`relaton` is pinned to `relaton/relaton@main`, which does *not* carry the OASIS
index-v2 producer yet. While that is true, `Relaton::Oasis::INDEXFILE` is
`index-v1`, the gem writes that file itself, and `index_builder.rb` reads it
back as its own reference index.

So a crawl still publishes a correct `index-v1`, and the committed
`index-v2.yaml`/`.zip` are **not refreshed by it** -- they hold the corpus as of
the crawl that produced them and go stale as `data/` moves.

The producer is unmerged and unpushed, and its branch ref carries no commit
above `main`, so no `git:` pin can reach it. Merging it -- see
`HANDOFFS/relaton__relaton__commit-oasis-index-v2-producer.md` -- turns
`index-v2` production back on here with no change to the `Gemfile`.

To regenerate `index-v2` before then, override the `relaton` line locally with a
`path:` pin to a working copy that carries the producer. Never commit that: the
location is machine-specific, so CI fails at `bundle install`.

`index_builder.rb` is correct either way. It reads `index-v2.yaml` when the
resolved gem writes one and falls back to `index-v1.yaml` when it does not, so
the pin never affects the `index-v1` this repository publishes.

== Browsable index

The `data/` directory is published as a browsable, crawler-indexable index at
https://relaton.github.io/relaton-data-oasis/.

`.github/workflows/deploy.yml` calls relaton/support's shared
`data-deploy.yml`, which builds the page with `relaton index` (relaton-cli reads
`data/` directly) and deploys it to GitHub Pages. The index files are not used
by that build.
